# Programmer Documentation

## 1. General Overview

### Purpose

FightSim resolves turn-based D&D 5e-style combat. It is built around one central design decision that shapes everything else in the program: **there is no separate representation for a player character versus a monster.** Every combatant — a goblin, a wizard, a horse — compiles down to the same `StatBlock` object. This mirrors how D&D 5e's own rules work: a monster's statblock and a character sheet ultimately describe the same kind of thing (abilities, HP, AC, a list of things it can do), even though they are usually presented very differently on paper. Treating them identically in code, rather than building a class hierarchy that distinguishes them, removes an entire category of special-casing throughout the rest of the program.

### Program Structure

The code is split across a small number of files, organized by namespace rather than by class-per-file, since most of these namespaces are short enough that splitting further would not aid readability:

- `FightSim.SimMath` — pure math with no game-rules knowledge: dice rolling, grid distance calculations (Chebyshev for movement/melee reach, Euclidean for ranged/spell range), and small tuple-arithmetic helpers.
- `FightSim` (root, in the `Program.cs`/`StatBlock.cs`-style file) — the `StatBlock` class itself, the `Ability`/`Condition` enums, the console-era `UserInterface` string-formatting helpers (now used to build log messages rather than print to a console), and the top-level `Program` class holding `TryMove` and `OrderByInitiative`.
- `FightSim.Actions` — the command-pattern action system: `CombatAction` and its subclasses, the `Resolution` static class of resolution primitives, the `ActionResult` struct, and the table-driven `ConditionRules` for advantage/disadvantage.
- `FightSim.States` — a state machine (`CombatStateMachine` and one class per state) driving the turn structure: whose turn it is, what input is currently expected, and what happens when an action or move resolves.
- `FightSim.Graphics` — the MonoGame-facing rendering layer: `Camera`, the `IDrawable` interface, and a small hierarchy of drawable UI primitives (`Box`, `Button`, `Bar`, `TextLine`, `Grid`, `Token`) plus composite types built from them (`Sidebar`, `LogBox`, `BattleMap`, `CombatantInitiativeBox`).
- `Game1.cs` / `CombatantSetup.cs` — the MonoGame entry point, using a `partial class` split specifically so that the combatant roster (which someone might want to edit without touching anything else) lives in its own file.
- `MouseInput.cs` — a small static wrapper around MonoGame's `Mouse.GetState()`, tracking current versus previous frame state to expose "was just clicked" rather than "is currently held."

### Key Design Decisions and Alternatives Considered

**Unified StatBlock instead of separate Player/Monster classes.** As above — a class hierarchy distinguishing player characters from monsters was considered and rejected, because in 5e's actual rules the two are not meaningfully different data shapes, only different *presentation* conventions. The unified model also means the combat engine (state machine, resolution primitives) never needs to know or care which "kind" of combatant it is operating on.

**Command pattern for actions, not an enum with a switch statement.** Every action (melee attack, ranged attack, heal, Dash, Shove) is a subclass of the abstract `CombatAction`, overriding a single `Resolve(attacker, target)` method. An enum-plus-switch design was considered, but rejected specifically because the list of action types is open-ended and expected to keep growing (more spells, more monster-specific actions in a future version) — an enum works well for a genuinely closed, fixed set of cases (it was used instead for `Ability` and `Condition`, which are fixed lists in the SRD), but forcing an ever-growing list of behaviorally distinct cases through one giant switch statement does not scale and mixes unrelated logic in one place.

**Resolution primitives as small, reusable, UI-blind functions.** `Resolution` contains no game-narrative logic — it exposes small operations (`RollAgainst`, `RollMagnitude`, `ApplyDamage`, `InReachMelee`, and so on) that every `CombatAction` subclass composes differently. This was a deliberate decomposition once it became clear early in development that every attack-like action was really three separable steps: rolling against a target number, rolling a magnitude, and applying that magnitude to a combatant. Keeping these as primitives rather than inlining them in each action meant that adding Shove (a roll-against-DC action with no damage roll) or `SingleTargetHeal` (a magnitude-and-apply action with no roll-against step at all) required no new resolution logic, only new combinations of existing pieces.

**`ActionResult`/`MoveResult` as UI-blind return values.** Every `Resolve()` and the movement function `TryMove` return a struct describing what happened, rather than printing or logging directly. This was a specific, deliberate decoupling decision made before the MonoGame UI existed: the combat-resolution logic was written and tested entirely against a console interface first, and later swapped for a graphical one, without a single change to any `CombatAction` subclass or to `TryMove`. Only the code that *reports* results (formerly `Console.WriteLine` calls, now string-building functions feeding a UI log box) needed to change.

**Advantage/disadvantage as a `RollType` parameter plus a table-driven condition lookup, not per-action special-casing.** `RollAgainst` takes a `RollType` (flat/advantage/disadvantage) rather than each action independently deciding how to roll. Which conditions grant advantage or disadvantage for which kind of roll is expressed as a dictionary (`ConditionRules.ConditionEffects`) keyed by `(Condition, RollContext)`, combined with a `CombineAdvantage(bool, bool)` helper implementing the 5e rule that any source of advantage and any source of disadvantage cancel out completely rather than stacking. This table-driven approach was chosen deliberately even knowing it would not cover every condition's full behavior — some conditions (Restrained's DEX-save-specific penalty, Incapacitated's effect on actions, Prone's movement cost) fall outside "does this modify a roll" and are handled as their own explicit checks elsewhere. The table is a genuine simplification for the common case, not a universal condition-effects engine, and was scoped that way on purpose rather than by accident.

**A `Camera`/relative-offset coordinate system for the UI, rather than storing absolute screen positions.** Every drawable object (`Box` and everything built on it) stores a position *relative to its parent*, and `IDrawable.Draw` takes the parent's absolute origin as a parameter, computing its own absolute position by addition at draw time. This was reworked partway through development, after an earlier version storing absolute `Rectangle` positions directly made every UI element implicitly depend on the exact screen layout it happened to be built inside. The relative version means a `Button` or `TextLine` has no idea where on screen it ultimately ends up — it only knows its offset from whatever contains it — which is what makes composite containers (`Sidebar`, `BattleMap`, `LogBox`) able to nest arbitrarily and be repositioned as a whole without touching their children.

**Recursive container drawing (`Box.Children` as `List<IDrawable>`).** Rather than every UI composite (sidebar, log, action panel) implementing its own draw logic from scratch, `Box` holds a list of anything implementing `IDrawable` (including other `Box`es) and draws them all with one recursive call. `LogBox` is the one exception, overriding `Draw` because which of its children are currently visible depends on scroll position, which an ordinary unconditional child loop cannot express.

**A `StatBlock` copy constructor instead of a from-scratch factory for duplicate monsters.** Spawning a second instance of an existing monster (e.g. a second goblin) is done via a constructor overload taking an existing `StatBlock` as a template, a new position, and an optional new name. It deep-copies mutable collections (`Actions`, `Scores`, `ACModifiers`) rather than sharing references, and deliberately resets `CurrentHP` and `Conditions` to a fresh state rather than copying the template's possibly-mutated values, since a freshly spawned combatant should not inherit whatever state the original happened to be in.

## 2. Detailed Breakdown

### StatBlock

The central data object. Holds a name, grid position, HP (current and max), AC (a base value plus a modifiers list, so temporary AC effects like Shield can be layered on without changing anything that reads `AC`), proficiency bonus, the six ability scores (stored in a `Dictionary<Ability, int>`, with computed modifier properties like `STRMod` for each), a `List<CombatAction>` of everything the combatant can do, initiative-related fields, a `HashSet<Condition>`, and movement tracking (`WalkSpeed`, `MovementRemaining`). Also exposes helper methods (`AddMeleeAttack`, `AddFinesseAttack`, `AddRangedAttack`) that construct the correct `CombatAction` subclass with the attacker's own ability modifier and proficiency bonus baked in, so combatant setup code never has to compute attack bonuses by hand.

### CombatAction and subclasses

`CombatAction` is abstract, exposing only `Resolve(StatBlock attacker, StatBlock target) -> ActionResult`. Subclasses:

- `MeleeAttack` / `RangedAttack` — roll to hit against the target's AC (checking reach first, using Chebyshev distance for melee and Euclidean for ranged), then roll and apply damage on a hit.
- `SingleTargetHeal` — rolls and applies healing to the target; no attack roll. Calling it with `target == attacker` works as a self-heal for free, since nothing in its logic assumes attacker and target differ.
- `Dash` — refills the attacker's movement by their walk speed.
- `Shove` — a fixed-DC contested-check simplification (see Limitations); on success, pushes the target one square directly away from the attacker.

`GenericActions` holds single shared instances of `Dash` and `Shove`, since both are stateless (no per-combatant data), so every combatant can safely reference the same object rather than each getting their own copy.

### Resolution

Static class of small primitives with no knowledge of `ActionResult` or logging: `RollAgainst` (roll a d20, optionally with advantage/disadvantage, compare to a target number), `RollMagnitude` (roll dice plus a flat modifier), `ApplyDamage`/`ApplyHealing` (clamp HP into range), `InReachMelee`/`InReachRanged`, `AddMovement`, `Move`, `ProneSwitch` (toggles the Prone condition), and `CombineAdvantage`.

### ConditionRules

Holds `ConditionEffects`, a dictionary mapping `(Condition, RollContext)` pairs to a `RollType`, and `GetAttackRollType`, which checks both attacker's and target's conditions against the table and combines the result. Used by `MeleeAttack`, `RangedAttack`, and `Shove` before calling `RollAgainst`.

### CombatStateMachine and states

Drives the turn loop. `CombatStateMachine` holds the combatant list, whose turn it currently is, transient selections (selected action, selected target combatant or tile), and references needed by states to interpret mouse clicks in world space (the camera, the battle map's screen bounds, square size). States: `TurnStartState` (resets movement/action-spent, skips unconscious combatants), `AwaitingActionState` (waiting for a button click), `AwaitingTargetCombatantState` / `AwaitingTargetTileState` (waiting for a map click, converting the click to a grid tile via `ScreenToGrid` and either finding a combatant there or accepting it as a move destination), `ResolvingActionState` / `ResolvingMoveState` (call into `CombatAction.Resolve`/`TryMove` and log the result), `EndTurnState`, and `GameEndState` (holds the winning combatant; `Game1.Draw` checks for this state and renders a dedicated win screen instead of the normal battle view).

### Graphics / UI layer

`IDrawable` is the single contract (`Draw(spriteBatch, pixel, font, parentOrigin)`) that every visual element implements. `Box` is the base container, storing a relative `Offset`, a `Size`, an optional background color, and a list of `IDrawable` children; its `Draw` method computes its own absolute position from the parent origin it is given, then recurses into its children with that as their new parent origin. `Button`, `Bar`, and `TextLine` are the leaf-level primitives (a clickable rectangle with a label, a fill-percentage bar, and a positioned string, respectively). `Grid` and `Token` bridge into the game's own coordinate system via `Camera` (which exposes `BoardOrigin`, the on-screen pixel position of grid square `(0,0)`, adjustable by `XShift`/`YShift` for panning) and the `GridToScreen`/`ScreenToGrid` conversion functions. `Sidebar`, `LogBox`, `BattleMap`, and `CombatantInitiativeBox` are composites built from the above — `CombatantInitiativeBox` in particular refreshes its child `TextLine`s and `Bar` from its `Combatant` field every draw call, since a combatant's live HP and initiative should never be baked into a static string at construction time.

### Communication Flow

`Game1.Update` polls `MouseInput`, advances `_stateMachine.Update()`, checks the current state to decide whether to rebuild the right sidebar's action buttons and handle sidebar clicks, checks for a win condition, and handles map panning and log scrolling. Clicking a button or grid square mutates `CombatStateMachine`'s selection fields and calls `TransitionTo`, which enters the new state's `Enter` method — this is where the actual rules-engine calls happen (`CombatAction.Resolve`, `Program.TryMove`), each producing a UI-blind result struct that gets formatted into a string (via `UserInterface`'s formatting helpers) and appended to the `LogBox`. `Game1.Draw` never touches game logic at all — it calls one method, `root.Draw(...)`, on the top-level `Box` containing the entire UI tree, and the recursive `Box.Draw` walk handles everything underneath.

## 3. What Was Not Implemented

Each of these was a deliberate scope decision, not simply something left unfinished for lack of time, though time constraints are naturally part of why the line was drawn where it was.

- **Reactions** (opportunity attacks, Shield, Counterspell, and any other trigger that interrupts another action mid-resolution). Every `Resolve()` call in this design is a single synchronous step; supporting reactions would require the resolution pipeline to be interruptible mid-call, which is a fundamentally different execution model than the rest of the engine uses, not an incremental addition to it.
- **Contested rolls in the general sense.** Shove is implemented as a flat-DC check (attacker's roll versus a DC derived from the target) rather than a true opposed roll, because `RollAgainst`'s whole design assumes one side rolls against a static number. Modeling genuine attacker-roll-versus-target-roll contests would mean either a second, structurally different resolution primitive, or complicating the existing one for a single action — the flat-DC simplification was chosen deliberately to avoid destabilizing a primitive that every other action already depends on.
- **Death saves.** A combatant at 0 HP is treated as fully down for the rest of combat rather than entering a stabilize/bleed-out subsystem. This avoids adding a second resource-tracking mechanic (death save successes/failures) that is orthogonal to everything else the engine tracks.
- **Spellcasting as a system** (spell slots, save-or-attack-roll distinctions per spell, area effects, concentration). `SingleTargetHeal` demonstrates that a spell-*shaped* action fits the existing `CombatAction` model without difficulty, but a full spellcasting system is its own vertical slice of complexity (a resource economy layered on top of the action system) and was scoped out of this version entirely.
- **Full condition coverage.** Only Prone, Restrained, Poisoned, Blinded, Grappled, and Incapacitated exist, and even for these, only the roll-modifying subset of their effects is implemented via the `ConditionEffects` table; conditions with entirely different mechanical effects (e.g. Paralyzed's auto-critical-on-hit) are not modeled.
- **Advantage/disadvantage on initiative rolls** (e.g. from the Alert feat). Only the DEX-modifier tiebreaker from the base rules is implemented.
- **A StatBlock/Combatant split.** `StatBlock` currently serves as both the reusable "template" (via the copy constructor) and the live, mutating combat instance simultaneously, rather than being split into an immutable template type and a separate mutable runtime type. This was a known tension from early in development and was deliberately deferred rather than solved, since a full split would touch essentially every file in the project for a benefit (cleaner separation of "what a goblin is" from "this specific goblin, mid-fight") that does not block anything in the current scope.
- **Zoom.** Panning (via click-and-drag) is implemented; zoom was considered and explicitly cut, since it would require every coordinate-conversion function in the `Graphics` namespace to account for a scale factor, a proportionally large addition for a feature that is not necessary to demonstrate the core simulator.
- **Proper clipping of off-screen tokens.** Tokens that would render outside the battle map's bounds (from panning) are currently skipped via a bounds check inside `Token.Draw` rather than a real GPU scissor rectangle; this is a functional but inelegant stopgap.
- **A main menu or in-program combatant selection UI.** The combatant roster is fixed at compile time in `CombatantSetup.cs`. This was a deliberate cut, not an oversight — building a UI for selecting/configuring combatants was judged to add substantial UI-layer work for no improvement to the actual thing being demonstrated (the combat engine), whereas editing one clearly-commented C# file achieves the same practical flexibility with far less code. The file was specifically split out via a `partial class` so that this editing can happen without needing to understand or touch anything else in the program.

## 4. Sources

Game rules referenced throughout are drawn from the publicly available D&D 5e System Reference Document (SRD). No third-party code libraries beyond MonoGame itself were used.

## 5. Final Thoughts

The two halves of this project — the rules engine and the MonoGame front end — ended up being very different kinds of work. The rules engine benefited enormously from being designed and tested through a plain console interface first; every `ActionResult`/`MoveResult` decision made early on to keep the engine UI-blind paid for itself directly when the console interface was later replaced with MonoGame's `IDrawable` UI tree without a single change to any action-resolution code. The UI layer was a much rougher process — MonoGame provides no layout system, no built-in UI widgets, and no event-based input, so a small amount of custom infrastructure (the relative-offset `Box`/`IDrawable` hierarchy, the click-detection state machine, the `Camera`/coordinate-conversion functions) had to be built from first principles before any of the actual combat UI could exist on top of it. Getting the grid, the tokens, and the sidebars to agree on a single consistent coordinate frame took considerably more iteration than any single piece of the rules engine did, which was a genuine surprise given how much more conceptually complex the rules side initially seemed.
